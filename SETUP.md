# HNU StallHub backend and account setup

## What is in this project

The existing project is a Next.js frontend and an Express/PostgreSQL API (using `pg`), not NestJS or TypeORM. The authentication, role checks, stall/menu routes, seller APIs, and customer order APIs in `backend` use that existing stack and can connect to Supabase PostgreSQL through its connection string.

The browser does not connect directly to Supabase and does not contain database credentials. The Express API verifies the account, sets an HTTP-only session cookie, and performs database access. `backend/schema.sql` is the complete PostgreSQL schema for a new, empty database. The Node.js backend is a separate service and is not pasted into the Supabase SQL editor.

## Supabase setup

1. Choose the database setup path:
   - **New, empty database:** run [`backend/schema.sql`](./backend/schema.sql) once as the database owner. It creates the application tables, status and audit enums, indexes, checkout procedure, inventory triggers, secure metrics view, categories, and starter tag catalog. It requires PostgreSQL 15+ for the view's `security_invoker` option. Then run [`backend/migrations/20261027_05_runtime_role.sql`](./backend/migrations/20261027_05_runtime_role.sql) and [`backend/migrations/20261027_09_product_soft_removal.sql`](./backend/migrations/20261027_09_product_soft_removal.sql) before continuing to step 4.
   - **Existing database:** back it up and apply the incremental migrations in step 3. Do not run `schema.sql` on an existing database; it is for a new, empty database only.
   In Supabase, `stall_operational_metrics` is a **view**, so look for it under Database > Views rather than Table Editor.
2. The project already has a private `backend/.env`; **do not overwrite it**. Add or update `DATABASE_URL` using your PostgreSQL connection string (use your provider's pooler if required), and add `SESSION_SECRET` with a private random string of at least 32 characters. Keep `.env` private.
3. For an existing database only, back it up, then run these PostgreSQL migrations in order from the Supabase/Neon SQL editor:
   - [`backend/migrations/20261027_02_order_status_enum.sql`](./backend/migrations/20261027_02_order_status_enum.sql) converts supported text order states to a PostgreSQL enum, or adds any missing lifecycle values to an existing enum.
   - [`backend/migrations/20261027_03_inventory_action_enum.sql`](./backend/migrations/20261027_03_inventory_action_enum.sql) adds audit labels to an existing `inventory_logs.action_reason` enum.
   - [`backend/migrations/20261027_04_database_automation_and_tags.sql`](./backend/migrations/20261027_04_database_automation_and_tags.sql) creates the `tags` and `product_tags` many-to-many tables with cascading tag-link cleanup, the `stall_operational_metrics` view, order checkout procedure, inventory deduction/audit triggers, and order-query indexes.
   - [`backend/migrations/20261027_05_runtime_role.sql`](./backend/migrations/20261027_05_runtime_role.sql) creates the non-login `stallhub_app` role and grants narrowly scoped table and routine permissions.
   - [`backend/migrations/20261027_07_secure_metrics_view.sql`](./backend/migrations/20261027_07_secure_metrics_view.sql) sets `stall_operational_metrics` to use the querying role's permissions and RLS (PostgreSQL 15+). Run it after the view is created.
   - [`backend/migrations/20261027_08_restore_admin_role.sql`](./backend/migrations/20261027_08_restore_admin_role.sql) ensures the admin role is allowed. Existing admin accounts remain unchanged.
   - [`backend/migrations/20261027_09_product_soft_removal.sql`](./backend/migrations/20261027_09_product_soft_removal.sql) adds a separate removal flag so sellers can remove products without deleting order history or confusing removal with marking an item sold out.
   - [`backend/migrations/20261027_10_menu_categories.sql`](./backend/migrations/20261027_10_menu_categories.sql) adds Meals, Drinks, and Snacks without creating case-insensitive duplicates, moves products assigned to Soup or Pasta into Meals, then removes those two category entries. Apply it after the other migrations.
   Run each file separately in this order; do not combine them in one transaction because PostgreSQL enum values added to existing enum types become usable after commit. These migrations expect the tables and columns shown in the current database diagram, in the `public` schema. Existing order statuses must be one of `Pending`, `Confirmed`, `Preparing`, `Ready for Pickup`, `Completed`, or `Cancelled`; map any other existing values before migrating. The automation migration expects `inventory_logs.action_reason` to be an enum or text-compatible field.
   After `tags` and `product_tags` have been created, optionally run [`backend/migrations/20261027_06_seed_starter_tags.sql`](./backend/migrations/20261027_06_seed_starter_tags.sql) to add reusable cafeteria tag labels without making assumptions about which products they describe.
4. In your database provider's role management page, create a dedicated **login** role with no superuser, database-creation, or role-creation privileges. Then grant it membership in `stallhub_app` (replace the identifier with the role you created): `GRANT stallhub_app TO stallhub_runtime;`. Set the backend `DATABASE_URL` to that login role. The API checks at startup that its connection is a non-superuser member of `stallhub_app`; it will refuse to start with an elevated or unconfigured account.
5. Create the first administrator from the `backend` directory with `npm run create-admin`. This one-time command asks for the administrator's School ID, name, and email, generates a strong password, and displays it once. Administrator accounts cannot be created through public registration.
6. For local development, the frontend uses `http://localhost:5000/api` by default. Set `NEXT_PUBLIC_API_URL` only if your API is hosted at another address. After the database migrations and roles are ready, start the API from `backend` with `npm install` (first time) and `npm run dev`; start the frontend from `frontend` with `npm install` (first time) and `npm run dev`.
7. Create a customer or seller account from the login page. Enter the assigned 8-digit School ID; the backend validates the role-specific ID format. Seller registration also asks for stall name and location, then creates the seller and stall together in a database transaction.
8. Run [`backend/reports/database_dictionary.sql`](./backend/reports/database_dictionary.sql) in the cloud database SQL editor after migrations and save/export its result sets for the required schema dictionary. Keep the provider's cloud backup and restore evidence with the final submission.

## Implemented workflow

- Login checks the stored password hash and selected role, then sets a signed, HTTP-only cookie. Customer and seller registration are database-backed; seller accounts are created with their own stall in one transaction.
- Customer pages show active stalls and products queried from PostgreSQL. Checkout derives customer identity, stall, product prices, and totals from the authenticated account/database. Customers can optionally add half-cup (₱8) or one-cup (₱15) rice to eligible viands; rice prices are validated and calculated by the API.

- Checkout validates customer choices in the API, then calls the PostgreSQL `place_order` procedure inside a transaction. The procedure locks product and inventory rows, rechecks active products and stall membership, calculates prices, and writes the order and item snapshots. An `order_items` trigger atomically deducts stock and rejects insufficient inventory; an `inventory` trigger writes signed stock changes to `inventory_logs`. The application does not separately decrement stock, avoiding duplicate deductions.
- Order lifecycle values are stored in the PostgreSQL `stallhub_order_status` enum when migrating the text-based column, and the dashboard status flow uses the matching enum values.
- Sellers can assign up to 10 tags to each product. `tags` and `product_tags` form the second many-to-many relationship, alongside products-to-orders through `order_items`; product tags are managed in the seller menu form.
- The starter tag catalog is seeded separately; sellers must assign labels such as `Vegetarian`, `Contains Pork`, or `Spicy` only when they are accurate for their menu items.
- Administrators have a protected dashboard to review campus activity and remove stalls from the customer menu. Stall removal deactivates the stall and its products instead of deleting records, preserving order history.
- Seller dashboard queries only the stall assigned to the authenticated seller. Product edits, inventory changes, order status transitions, and payment recording check ownership on the backend. Customer history is filtered by the authenticated customer.
- Sellers can open their profile from the dashboard header to upload a JPEG, PNG, or WebP stall cover photo up to 10 MB, or remove it. Account removal requires the current password and typing `DELETE`; it disables and anonymizes the seller and stall, hides products, and preserves historical orders.
- Order preparation transitions are `Pending → Confirmed → Preparing → Ready for Pickup`. When the customer pays at pickup, the seller records the payment method received; the API records the full order amount in `payments` and marks the order `Completed` in one transaction. Sellers can also record a missing payment for a previously completed order. Completion cannot be marked through the regular status endpoint without recording payment. Product removal is a soft removal so completed order details remain available.

## Before deployment

- The repository includes [`render.yaml`](./render.yaml) for deploying the Next.js frontend and Express API as separate Render web services. In Render, create a Blueprint from the GitHub repository and select the `master` branch (or whichever branch contains this file).
- Both services are configured with Render's `free` plan. Free web services sleep after 15 minutes without traffic and can take about a minute to wake up; they are best for demos and testing, not production. Render's free instance hours are shared across services in the workspace, so monitor usage in the Render dashboard.
- Enter `DATABASE_URL` and `SESSION_SECRET` as private environment values for the `hnu-stallhub-api` service. Do not put database credentials or session secrets in GitHub or frontend environment variables.
- The frontend uses a same-origin `/api` path. Next.js proxies those requests to the backend using the API's public `onrender.com` URL in `BACKEND_URL`. Do not use the API's internal hostname here: free Render web services cannot receive private-network requests. The proxy keeps the browser session cookie same-site; the backend CORS setting is not needed for this proxy path.
- Locally, `BACKEND_URL` defaults to `http://localhost:5000`; run the backend and frontend in separate terminals. Local database access still needs `DATABASE_URL` and `SESSION_SECRET` in `backend/.env`.
- Use the Supabase PostgreSQL connection URI (Session Pooler if required by your network) for the API service. The database connection is used by the backend only.
- Production API startup rejects localhost database hosts and superuser database connections. The live deployment and cloud firewall still need to be verified in the database provider and hosting dashboards.
- After migrations and representative cloud data are in place, run `npm run benchmark-db` from `backend` to execute `EXPLAIN (ANALYZE, BUFFERS)` for the customer order history, stall order list, and order detail queries. Save the output as the measured benchmark report; do not present results from an empty/local database as production measurements.
- Existing tables and data cannot be verified from this workspace because no database schema export or usable database credentials were provided.
